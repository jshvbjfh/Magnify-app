§ 1

The machinery as it stands

Five tables carry the whole stock-and-sales story. Understanding which one is the key matters more than the field list, because the redesign turns on exactly one of them.

TableWhat it really isIdentityStation lock
inventory_items The ingredient card — name, unit, running quantity, current unitCost. Also holds preps (type='prep'), which carry no stock of their own. cuid, unique on (restaurantId, branchId, name) hard branchId required
inventory_purchases This is the batch. One row per stock entry, with remainingQuantity as its live balance. FIFO consumption walks these rows oldest-first and decrements them. cuid is the real key; batchId is a printable label like B-07202026-A3F9K2 and is nullable hard branchId required
dish_ingredients The recipe. quantityRequired of one specific ingredient card per one serving. (dishId, inventoryItemId) implicit — inherited from the item it points at
inventory_batch_usage_ledgers The audit trail. One immutable row per batch touched, tagged sourceType = dishSale / waste / adjustment / prepProduction. cuid + (sourceType, sourceId) index stamped — copied from the consumption
dish_sales + dish_sale_ingredients The COGS record written at payment. The sale row carries the station that owns the dish; the ingredient rows carry what it actually cost. cuid, deduped on orderItemId already flexible
The batch is a purchase row. There is no separate batch table — batchId is a human label, and consumption falls back to the row id when it's null.

What happens when a waiter takes payment

This is the path every gram travels. It starts in lib/restaurantOrderPayment.ts and ends inside lib/inventoryConsumption.ts.

Order marked PAID — pushed from the waiter device or paid in the portal
finalizeRestaurantOrderPayment() loads the order's ACTIVE items.
Each line resolves its own station
item.branchId (snapshotted when it was rung up) → else the dish's live branchId → else the till's. One order can legitimately span stations, and already does.
A DishSale row is created per line, stamped with that station
Idempotent on orderItemId, so a replayed push can't double-consume.
MEP first, at dish level
Batch-cooked preparedPortions cover the sale before the recipe runs at all; only the uncovered remainder reaches the recipe.
For each recipe row: prep-aware or straight consumption
A prep drains its own kitchen-made layer first, then cascades the shortfall to its raw sub-recipe. Everything else goes straight to FIFO.
▸ The station gate — consumeIngredientStock()
The ingredient card is looked up by (id, restaurantId, branchId) and the FIFO layers by (ingredientId, restaurantId, branchId). This is the entire per-station stock model.
Layers decrement oldest-first; a ledger row is written per layer
Then inventory_items.quantity takes a relative decrement and unitCost is repointed at the new front layer.
Journal entry, then everything is queued to the sync outbox
Revenue and COGS post double-entry; the changed rows fan out to devices.

The failure mode you're living with

When the selling station's ingredient card doesn't exist, consumeIngredientStock throws Ingredient … was not found, and dishSaleRecording.ts catches it and silently skips COGS for that line. Revenue still posts. The sale just records a food cost of zero. That's deliberate — throwing would trap the order in a retry loop — but it means missing stock shows up as fake profit, not as an error.

§ 2

Where the lock actually lives

The per-station stock model isn't spread across the codebase the way the table count suggests. Thirty-four non-test files reference the inventory tables, but only three places enforce that a dish can only eat from its own station's shelf.

LocationWhat it enforcesEffect if changed
lib/inventoryConsumption.ts — item lookup, ~L86–99 The ingredient card must belong to the consuming station. Sales stop failing to find shared ingredients.
lib/inventoryConsumption.ts — layer query, ~L115–123 FIFO batches must belong to the consuming station. Consumption draws from the shared pool.
app/api/restaurant/dishes/[id]/ingredients/route.ts — L44 A recipe may only reference an ingredient in the manager's currently-selected station. Recipes at any station can point at Main's items.
Verified against the current tree. Everything else — reports, the integrity checker, MEP, waste, stock-take — reads the same shape and follows once these agree.

Why this matters for scoping

You don't need to rip branchId out of the inventory tables, and you shouldn't. Keep the column, keep every existing row where it is, and introduce one resolver that answers "which station's shelf does this consumption read from?" Per-station mode returns the station; shared mode returns Main. The schema doesn't move; the question changes.

Read the 29% carefully before blaming the model

Zero-cost sales have several possible causes — a dish with no recipe at all, an ingredient not yet synced from a device, genuinely empty stock. Splitting that 36 into causes is a half-hour query, and it's worth doing first: it tells you how much of the pain shared stock actually removes versus how much is missing recipes, which shared stock will not fix.

§ 5

Proposal — Main as the mother stock

Stations draw straight from Main. No per-station shelves, no issuing paperwork, one number per ingredient. Recipes at every station point at the same ingredient card.

The core change

One resolver, called from the places that read or write stock. Nothing else needs to know shared mode exists.

// lib/stockScope.ts  — new
export async function resolveStockBranchId(
  db, restaurantId: string, sellingBranchId: string,
): Promise<string> {
  // Per-station mode keeps today's behaviour exactly.
  if (!(await isSharedStockEnabled(db, restaurantId))) return sellingBranchId
  // Shared mode: every consumption reads Main's shelf.
  return (await getMainBranchId(db, restaurantId)) ?? sellingBranchId
}

Then consumeIngredientStock resolves once at the top and uses the result for the item lookup and the layer query — while continuing to stamp the selling station onto the ledger row, so per-station usage reporting survives intact. That distinction is the whole design: stock is read from Main, usage is attributed to the station that sold it.

The data merge — the genuinely risky part

Twenty-one duplicated ingredients have to become one. Two hard constraints shape how:

  • Resolve the 11 unit conflicts first, by hand. Merging potato: 25,500 g with potato: 0 kg without agreeing a unit produces a silently wrong number that then costs every potato dish wrongly. This is a decision, not a script.
  • Re-point, never re-create. Move existing cards and batches to Main by updating branchId, and re-point dish_ingredients.inventoryItemId at the surviving card. Do not create new InventoryItem or InventoryPurchase rows in a migration script — a new batch is a new FIFO layer and a phantom purchase in the accounts.

Where two stations hold the same ingredient, the surviving card's quantity must be recomputed from the merged layers rather than added arithmetically, so the running total and the batch balances can't drift apart.

What this design does not give you

  • No per-station stock variance. With one shelf, "the bar is losing gin" becomes unanswerable from stock counts — you can still see it through per-station usage in the ledger, but a physical count at Main can't tell you which station lost it.
  • No station-level stock-outs. Every station sees the same availability, which is right for a shared pantry and wrong for a bar that physically holds its own bottles. Your data shows exactly this split: the spirits duplicated between stations 2 and 6 are almost certainly two real, physically separate bars.
  • Physical reality still has to match. One number in the app across seven rooms only stays honest if the stock is genuinely stored and counted centrally.

If the bars turn out to need their own bottles, the hybrid variant — station shelf first, fall through to Main — is the same resolver returning a list instead of a single id. Worth keeping the door open in the interface shape even if you don't build it now.

Ordered so that each phase is independently useful and independently reversible. Estimates assume the existing test suite is kept green.

PHASE 1Make the damage visible~1 day

  • Report on duplicate cards, unit conflicts and cost conflicts as a screen, not a script.

  • Default off. No existing restaurant changes behaviour.
PHASE 3Entry and recipe surfaces~2–3 days
  • Stock entry writes to Main in shared mode; the ingredient picker offers Main's catalogue at every station.

PHASE 4Merge one restaurant, watched~1–2 days + observation
  • Agree the 11 units by hand. Re-point cards, batches and recipes to Main. Recompute quantities from layers.

  • Verify against the live DB before and after; do not migrate blind.

The APC report

Average per cover. Independent of everything above — no shared reason to sequence them together, and it's much cheaper.

MetricAvailable now?Source

Average per cover (per guest)noNothing records how many guests sat down. RestaurantTable.seats is table capacity with a default of 4 — using it would report table size, not guests, and would be wrong on every shared or partly-filled table.

To get true per-cover

  • RestaurantOrder.guestCount Int? — nullable, so historical orders stay honest rather than being back-filled with a guess.
  • A guest-count step when the waiter opens a table, in both waiter apps (waiter-app and waiter-app-desktop), carried through the local SQLite order row and /api/mobile/push.
  • The report shows per-cover only for the covered date range and states the coverage — a partial denominator quietly reported as a full one is worse than not reporting it.

Roughly a day for the report against what exists, plus a day or so for the guest-count capture across both apps and the sync path. The report is worth shipping first on per-check while the covers data accumulates — per-cover is meaningless until you have a few weeks of it anyway.

§ 8

Decisions I need from you

  1. Are the two bars physically separate? Stations 2 and 6 both hold Jack Daniel, Olmeca, Bacardi, in different units and at wildly different costs. If those are two real bars with their own bottles, pure shared stock will misreport both, and the hybrid is the right answer for drinks even if the kitchen shares one pantry.
  2. Is stock physically stored centrally? One number across seven rooms is only true if someone counts it in one place.
  3. Whose call are the 11 unit conflicts? Potato in g or kg, egg in pcs or piece, spirits in shots or ml. Someone who knows the operation has to decide, and it blocks the merge.
  4. Roll out to all restaurants or one? The flag makes per-restaurant rollout free. I'd migrate the seven-station account first and leave everyone else untouched.
  5. Ship the APC report on per-check now, or wait for covers? My recommendation is ship now and add the per-cover line once the guest counts have accumulated.
