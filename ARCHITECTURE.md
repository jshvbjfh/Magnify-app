# Magnify — Table Structure & Sync Architecture

## Roles

| Role | Identity model | App | Database |
|---|---|---|---|
| **Admin / Manager** | `User.role = "admin"` | Web portal (Vercel) + Magnify Electron desktop | PostgreSQL (Neon) / local SQLite |
| **Owner / Investor** | `User.role = "owner"` | Android APK — Capacitor WebView → `https://magnify-app-tau.vercel.app` | No local DB — reads PostgreSQL via Vercel API; credentials created by admin |
| **Waiter** | `Staff` model (NOT `User`) | Magnify POS (Electron) or PWA | Local SQLite — syncs with Vercel via `/api/mobile/pull` and `/api/mobile/push`; JWT `sub = Staff.id` |

> **Owner APK notes:** Built with Android Studio from the `android/` folder in this repo (Capacitor shell).
> Web-only changes (UI, data) deploy automatically via Vercel — no APK rebuild needed.
> APK rebuild is only required for native config changes (app ID, permissions, Capacitor plugins).

```
restaurant_tables
 ├─ id (cuid)

 ├─ id (cuid)  ← generated by client (waiter app)
```

## 3. Pull Detail

```
GET /api/mobile/pull?branchId=<id>
────────────────────────────────────────────────────────────────

Auth:   JWT  { sub: staffId, restaurantId, branchId, role }
         └─ sub is a Staff.id  (NOT a User.id)

Branch resolution (server):
  1. ?branchId param present AND belongs to this restaurant  → use it
  2. fallback to JWT branchId

Response:
  {
    dishes:   [ { id, name, selling_price, category, is_active,
                  branch_id, restaurant_id } ]          ← branch-scoped

    tables:   [ { id, name, seats, status,
                  branch_id, restaurant_id } ]           ← branch-scoped

    branches: [ { id, name, code, isMain } ]             ← ALL active branches
                                                           (drives branch chips)
    restaurant:  { id, name }

    cancellationApprovers: [ { id, name, pin_hash } ]    ← staff with PIN
                                                           (offline cancel auth)
  }

Client (waiter-app-desktop):
  replaceDishes(dishes)  → DELETE WHERE branch_id = ?  + re-insert
  replaceTables(tables)  → DELETE WHERE branch_id = ?  + re-insert
  store branches in restaurant_config as JSON
  update activeBranchId if branch switch was requested
```

## 4. Push Detail

```
POST /api/mobile/push
────────────────────────────────────────────────────────────────

Auth:   Same JWT as pull

Body:
  {
    orders:     [ MobileOrder ]
    orderItems: [ MobileOrderItem ]
  }

Per order — branch resolution (server):
  validBranches = SELECT id FROM branches
                  WHERE restaurantId = ? AND isActive = true

  resolvedBranchId = order.branch_id ∈ validBranches
                       ? order.branch_id      ← honours branch switch
                       : JWT.branchId         ← fallback

Per order — upsert logic:
  UPSERT restaurant_orders  WHERE id = order.id
    ├─ NEW order   → create with resolvedBranchId, status = PENDING/OPEN
    └─ status=PAID AND not yet paid on server
         → run finalizeRestaurantOrderPayment()
              ├─ mark order PAID
              ├─ create dish_sales  (one per dish)
              ├─ deduct inventory   (FIFO batches)
              ├─ create journal_entry + journal_lines  (double-entry)
              └─ enqueue to sync_outbox

Per order — UPSERT order_items  WHERE id = item.id
  (totalPrice defaults to 0 — server recalculates order totals)

Response:
  { ok, syncedOrderIds, failedOrderIds, failedOrders }
```

## 5. Branch Switch Flow (waiter-app-desktop)

```
Waiter taps branch chip
        │
        ▼
Wait for syncingRef === false  (up to 10 s)
        │
        ▼
runSync({ branchId: newId, persistBranch: true })
        │
        ├─► pushSync()          push any pending local orders first
        │
        └─► pullSync(newId)     GET /api/mobile/pull?branchId=newId
               │
               ├─ replaceDishes  DELETE WHERE branch_id = newId  → insert
               ├─ replaceTables  DELETE WHERE branch_id = newId  → insert
               └─ loadStoredBranchState()  → update branch chips UI
        │
        ▼
On success (no error, no warning):
  setConfig('activeBranchId', newId)
  setConfig('branchId', newId)          ← new orders will carry this branch_id
        │
        ▼
getDishes(activeBranchId)   ← filtered by branch_id
getTables(activeBranchId)   ← filtered by branch_id
getOrders({ branchId })     ← filtered by branch_id
```

## 6. Order Lifecycle

```
WAITER APP                          SERVER (on push)
──────────────────────────────────────────────────────────────────────────

[1] Waiter builds cart
      └─ dishes from local SQLite (branch-filtered)

[2] confirmOrder()
      ├─ orderId = cuid()
      ├─ orderNumber = "WA-" + orderId.slice(-8)
      ├─ branch_id = activeBranchId (from config)
      └─ INSERT INTO orders + order_items (status = PENDING, synced = 0)

[3] pushSync()
      └─ POST /api/mobile/push
           └─ upsert restaurant_orders (status = OPEN)
              upsert order_items

[4] Kitchen prepares → waiter marks "served" (manager portal)
      └─ PATCH /api/restaurant/orders/[id]  action=serve

[5] Payment
      Waiter:  order.status = PAID locally → pushSync()
      Server:  action=pay  OR  push with status=PAID
                 ├─ finalizeRestaurantOrderPayment()
                 │     ├─ dish_sales  (1 per dish, with COGS)
                 │     ├─ inventory deduction  (FIFO batch consumption)
                 │     ├─ journal_entry  (double-entry: revenue + COGS)
                 │     └─ mark table "available"
                 └─ enqueueOrderSync → sync_outbox

[6] Cancel / Waste  (requires supervisor PIN)
      Server:  action=cancel  OR  action=waste
                 ├─ order_items → status=CANCELED / WASTED
                 ├─ restaurant_order → status=CANCELED
                 ├─ table → status="available"
                 └─ enqueueOrderSync → sync_outbox
```

## 8. Legacy SQLite Compatibility Repair

Old Electron installs (`dev.db`) were created before the branch system existed. They are missing tables and columns that the current Prisma schema requires. On every boot, `electron/main.js` runs a **targeted compatibility repair** before handing off to `prisma db push`.

```
Electron boot
  │
  ├─ prisma db push --accept-data-loss
  │     └─ FAILS if any NOT NULL column has existing NULLs  ("cannot be executed")
  │
  ├─ Compatibility repair  (electron/main.js: runCompatibilityRepair)
  │     │
  │     ├─ users              ADD isActive (DEFAULT 1), isSuperAdmin (DEFAULT 0)
  │     ├─ restaurants        ADD managerId, fifoEnabled, fifoConfiguredAt,
  │     │                         syncRestaurantId, deletedAt
  │     │
  │     ├─ branches           CREATE TABLE IF NOT EXISTS  ← key for pre-branch DBs
  │     │                     INSERT default branch per restaurant if none exists
  │     │                         id = 'branch-' + restaurantId
  │     │                     ADD deletedAt
  │     │
  │     ├─ dishes             ADD description, deletedAt
  │     ├─ restaurant_tables  ADD deletedAt
  │     ├─ restaurant_orders  ADD staffId, notes, journalEntryId, deletedAt
  │     │
  │     ├─ inventory_items    ADD restaurantId, branchId (+ backfill from orders/branches)
  │     │                     ADD description, deletedAt
  │     ├─ inventory_purchases ADD paymentMethod (DEFAULT 'Cash'), journalEntryId, deletedAt
  │     │
  │     ├─ dish_ingredients   ADD inventoryItemId (+ backfill from ingredientId), updatedAt
  │     ├─ dish_sales         ADD restaurantId, branchId (+ backfill), dishName,
  │     │                         updatedAt, deletedAt
  │     ├─ dish_sale_ingredients ADD updatedAt
  │     └─ branch_devices     ADD restaurantId (+ backfill)
  │
  ├─ prisma db push --accept-data-loss  (retry — NULLs now filled, branches table exists)
  │     └─ Creates ALL missing tables: staff, staff_branches, employee_shifts,
  │        order_items, journal_entries, journal_lines, waste_logs, categories,
  │        accounts, inventory_adjustment_logs, inventory_batch_usage_ledgers,
  │        sync_cursors, sync_outbox, sync_conflict_logs
  │
  └─ App boots normally
```

**Why `branches` must be created in the repair (not by `db push`):**
`db push` refuses to run at all when it detects "cannot be executed" changes (NOT NULL columns with existing NULLs). The NULL `branchId` values on `dish_sales` and `inventory_items` block `db push` entirely — including new table creation. The repair creates `branches` and seeds a branch first so the fallback UPDATEs can fill those NULLs, unblocking the retry.

**First-boot after upgrade — staff table is empty:**
`staff`, `staff_branches`, and `employee_shifts` are created empty. The admin must create at least one staff account (Employees section in the manager portal) and assign them a branch before the waiter app can authenticate against `/api/mobile/pull`.

## 9. Known Limitations

| # | Area | Detail |
|---|---|---|
| 1 | Manager portal branch | `getRestaurantContextForUser()` always returns the MAIN branch. All admin API routes (tables, dishes, orders, inventory) are locked to the main branch. Multi-branch admin view requires session-level branch storage. |
| 2 | `sync_outbox` | Populated on every table/order change but not yet consumed by any polling client. The waiter pull does fresh DB reads instead. Ready for a future Electron ↔ cloud sync daemon. |
| 3 | Schema drift | `@@unique([restaurantId, orderNumber])` in Prisma vs `(restaurantId, branchId, orderNumber)` unique index in PostgreSQL. No crash impact (routes use `id` for lookups) but Prisma migrations would conflict. |
| 4 | `order_items.totalPrice` | Always pushed as 0 from the client. Server recalculates order-level totals at payment time but not per-item totals for pending orders. |
| 5 | Legacy seeded branch | Pre-branch DBs get a branch with `id = "branch-" + restaurantId` and `isMain = true`. This branch has no `code` uniqueness guarantee across restaurants (all get code `"MAIN"`), but since each is scoped to its own `restaurantId` the unique index `(restaurantId, code)` is satisfied. |
